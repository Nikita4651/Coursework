## Перечень автоматизируемых сценариев
Одну форму (обычная оплата ) и автоматизирую её. Для начала хватит 4–6 позитивных и негативных кейсов:


_Позитивные:_

1. Покупка тура обычной картой (APPROVED: 1111 2222 3333 4444) → статус «Success» в UI, запись в БД со статусом «APPROVED».

2. Покупка тура в кредит той же картой → статус «Success», запись в БД со статусом «CREDIT_APPROVED».


_Негативные:_


1. Оплата картой DECLINED (1111 2222 3333 4444) → сообщение об ошибке, в БД статус «DECLINED».

2. Пустые поля формы → валидационные сообщения.

3. Некорректный CVC (не 3 цифры) / истекший год → валидация на фронтенде.

4. (Опционально) Невалидный формат карты → проверка, что приложение не сохраняет данные карт.


_Для каждого кейса сразу фиксирую:_


_А._ входные валидные данные:,

1. Карта (1111 2222 3333 4444)
2. Месяц (08)
3. Год (26)
4. Владелец (Ivan Ivanov)
5. cvc (111)

_Б._ входные невалидные данные:,

1. Пустые поля
2. Не существующая карта (0000 2222 3333 4444)
3. Прошлый и следующий месяц (07),(09)
4. Прошлый и следующий год (25). (27)
5. Владелец с дефисом, с (й.ё),со спец символами, с цифрами
6. cvc меньше 3 цифр (11)


_В._ ожидаемый результат (в UI и в БД),

_Д._ способ проверки (Selenide + SQL-запрос).



_Инструменты и обоснование_

1. Java + Selenide — UI-тесты, удобно для Page Object.

2. JUnit 5 — запуск тестов, привычная структура.

3. Gradle — сборка и запуск тестов; у меня уже есть опыт с build.gradle и настройкой зависимостей.

4. Allure — отчёты по тестам (красивые репорты с шагами, вложениями, скриншотами).

5. JDBC + JUnit (или простой DAO) — проверка записей в БД после теста. Это закрывает требование «запросы в базу».

6. Docker / Docker Compose — локально можно поднять MySQL, чтобы тесты были воспроизводимыми.

7. Git — публичный репозиторий, README с инструкцией запуска.


_Риски и оценка времени_


1. База данных не успевает запуститься → тесты падают с ошибкой соединения. Решение: добавить ожидание (healthcheck) использовать библиотеки типа Testcontainers (если разрешено).

2. Разные СУБД (MySQL vs PostgreSQL) → SQL-синтаксис и типы данных отличаются. Решение: писать параметризированные тесты или отдельные конфигурации.

3. Симулятор банковских сервисов перегружен → таймауты. Решение: повторные попытки (retry) или увеличение таймаутов.

4. Проблемы с сетью/IP в логах → сложно отлаживать. Решение: фиксировать свой IP и искать логи по нему.


_Оценка_


1. Планирование: 4–10 часов.

2. Написание тестов (4–6 кейсов): 12–26 часов.

3. Настройка Allure, Docker, README: 8–18 часов.

4. Прогон, оформление баг-репортов, отчётов: 8–20 часов.

Итого: ориентировочно 42–76 часов (с учётом рисков и отладки).


_План сдачи:_


1. День 1–3: план, выбор формы, настройка окружения.

2. День 4–8: написание и отладка тестов.

3. День 8–10:  отчёты, баг-репорты.

4. День 13: финальная проверка README, загрузка в репозиторий.
